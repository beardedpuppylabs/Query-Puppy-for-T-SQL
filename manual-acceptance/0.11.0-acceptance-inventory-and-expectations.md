## Feature Inventory

### Editor Integration And Configuration

- VS Code/VSCodium SQL activation on `onLanguage:sql`.
- Native CompletionItemProvider and SignatureHelpProvider.
- Native Suggest UI only; no custom editor UI and no Microsoft completion
  scraping/post-filtering.
- Commands: expand `SELECT *`, refresh metadata, clear active database cache,
  show status, disable Microsoft SQL suggestions, diagnose Signature Help,
  diagnose Query Scope.
- Settings: extension enablement, debug logging, Smart Alias enablement.
- Tab-only wildcard expansion context key; Enter must not expand.
- Microsoft `mssql` suggestions are handled by explicit user consent/command only.

### MSSQL Connection And Metadata Lifecycle

- Reuses the active Microsoft `ms-mssql.mssql` connection-sharing API.
- Active connection/database lookup remains dynamic.
- mssql API acquisition and active-context lookups are coalesced and retryable.
- Catalog loads are read-only, set-based, per connection/database identity.
- Secondary databases are loaded lazily only after explicit qualification.
- Versioned persistent canonical snapshots live in `globalStorageUri`.
- Snapshot identity is hash-based from connection ID plus database name.
- Warm hydration rebuilds runtime `DatabaseIndex` immediately.
- First use per extension session schedules one non-blocking refresh.
- Later refresh eligibility is demand-driven after 15 minutes.
- Manual refresh bypasses freshness but uses the same coalesced refresh path.
- Refresh failures preserve the last usable memory and disk snapshot.
- Cache clear is active-database scoped and confirmed.

### Completion Pipeline

- Matching is case-insensitive contiguous Contains.
- No StartsWith-only, fuzzy, prefix bonus, or substring-position bonus behavior.
- Explicit exact textual priority may rank the exact item first.
- Deterministic sorting within equivalent semantic/ranking tiers.
- Explicit qualifier resolution is strict: `alias.` returns only that RowSource.
- Semantic candidates are created before filtering/ranking/materialization.
- Physical columns use one canonical CompletionItem factory.
- Physical-column rows preserve complete filterText, insertText, metadata and docs.
- Long names are visibly bounded but insert/filter using the complete identifier.
- Type groups are decorative, insert nothing, and never become semantic columns.

### Row-Source And Object Completion

- `FROM`, `JOIN`, and `APPLY` source completion includes schemas, tables, views,
  TVFs, synonyms where loaded, and visible local RowSources.
- Active-database schemas participate in unqualified source completion.
- Database-qualified forms include `Database.`, `Database.Schema.`,
  `Database.Schema.Object`, and `Database..Object`.
- Database-wide shortcut `Database.fragment` searches schemas and schema-qualified
  objects across schemas while preserving legal insertion.
- Four-part/Linked Server intelligence is out of scope.
- Curated developer metadata includes selected `sys` views and common
  `INFORMATION_SCHEMA` views without broad system-object noise.

### QueryScopes And Document-Local Semantics

- QueryScopes are nested, local-first, and position-sensitive.
- Legal correlated outer aliases are visible in expression subqueries.
- Sibling scopes and future aliases are isolated.
- Alias shadowing is local-first.
- Ordinary derived tables do not correlate.
- `CROSS APPLY` and `OUTER APPLY` may see left-side sources.
- CTEs support projections, explicit column lists, ordering of definitions, and
  conservative recursive behavior.
- Temp tables, table variables, `SELECT INTO`, straightforward `ALTER TABLE ADD`,
  derived tables, `VALUES`, and APPLY projections expose local RowSources.
- Projection aliases are visible where SQL Server permits them, notably `ORDER BY`.
- Set operations (`UNION`, `UNION ALL`, `INTERSECT`, `EXCEPT`) compose result
  columns by ordinal using the first branch's names.

### Schema Intelligence

- Catalog metadata includes schemas, tables, views, scalar functions, TVFs,
  procedures, parameters, types, synonyms, sequences, physical columns, PK, UQ,
  unique indexes, FKs, and relationship mappings where supported.
- Physical columns display compact roles: `PK`, `UQ`, `FK`, and combinations.
- Composite constraints preserve ordinal mapping.
- Filtered unique indexes remain distinguishable from ordinary unique constraints.
- INCLUDE columns are not unique-key members.
- Principal columns are not incorrectly marked FK due to incoming references.
- Same-named objects in different schemas/databases remain isolated.

### JOIN Intelligence

- FK JOIN predicates are generated from actual enabled cached FK metadata.
- Current-right alias is rendered first.
- Reverse query order works.
- Multiple FKs between the same tables remain separate candidates.
- Composite FKs produce one ordered predicate.
- Cross-schema FKs work inside one database.
- Disabled FKs and unrelated same-name/type heuristics do not generate predicates.
- JOIN source ranking boosts related tables after Contains filtering.
- FK relationship inference does not cross database boundaries.
- ON-clause visibility is positional and cannot see future JOIN aliases.

### DML And Callable Objects

- INSERT target-list completion offers writable target columns.
- UPDATE SET LHS offers writable target columns.
- Identity, computed, generated, hidden, and rowversion columns are excluded from
  writable target suggestions.
- UPDATE RHS, INSERT VALUES, and INSERT SELECT can derive ExpectedType.
- DELETE scope stays statement-correct.
- OUTPUT supports valid `inserted`/`deleted` pseudo sources with full column
  metadata.
- Invalid pseudo source contexts are not broadened.
- EXEC/EXECUTE named parameter completion preserves declaration order, excludes
  already used parameters, and displays OUTPUT parameters.
- Scalar UDF and TVF Signature Help use shared callable parsing.
- Stored-procedure result-set discovery remains deliberately unsupported.

### Type Intelligence

- Normalized SQL types preserve facets such as length, precision, scale,
  nullability, and UDT identity.
- Compatibility tiers cover exact, same base type, compatible family, unknown,
  and incompatible.
- Physical/query-local columns, literals, CAST, CONVERT, scalar UDF returns,
  arithmetic, conservative CASE, ISNULL/COALESCE where recognized, and set results
  can participate in type inference.
- ExpectedType sources include comparison operands, function arguments, UPDATE,
  INSERT, LIKE, and arithmetic.
- Type-aware completion ranks rather than hides visible candidates.
- Without a reliable ExpectedType, no type groups or type sorting are applied.
- User-facing groups may be `Type match · <type>`, `Compatible <family>`, and
  `Other visible columns`.

### Built-In Function Intelligence

- Static built-in catalog is immutable, case-insensitive, connection-independent,
  and does not initialize schema metadata.
- Supported built-ins: `CHARINDEX`, `DATEADD`, `DATEDIFF`, `DATEFROMPARTS`,
  `ROUND`, `STRING_AGG`, `SUBSTRING`.
- Built-ins appear in expression completion, not row-source completion.
- Built-ins use shared call-site parsing, Signature Help, ExpectedType, and return
  inference.
- SQL Server 2022 semantics are used; `DATEADD` bigint-preview behavior is not
  treated as available.

### Productivity

- `SELECT *` and `alias.*` can expand with Tab using semantic RowSource columns.
- Smart Alias suggestions appear only after a syntactically complete RowSource and
  separating whitespace or `AS`.
- Smart Alias suggestions insert only the alias snippet, never `AS` or the
  RowSource.
- Existing aliases suppress redundant alias suggestions.
- Collision fallback is deterministic and scoped to legally visible QueryScopes.
- Exact shorter object names must not suppress longer legal Contains candidates.

## Existing Fixture Coverage And Gaps

### What Is Already Strong

- `tests/fixtures/create-schema-intelligence-fixture.sql` covers `reltest` and
  `relref` for PK/UQ/FK metadata, three parallel address FKs, composite
  PK/composite FK, cross-schema FK, filtered unique index, INCLUDE safety,
  disabled/untrusted FK state, and relationship-based JOIN tests.
- Unit/provider/Extension Host tests cover the semantic contracts without a live
  database.
- `tests/persistent-metadata.test.ts` covers the persistent 0.11.0 lifecycle with
  deterministic stores and injectable time.

### Current Fixture Gaps

The repository does not currently contain one complete SQL provisioning script for
all manual acceptance features. Live integration and Extension Host tests expect
several real/manual fixtures that are not fully created by the two checked-in SQL
scripts:

- Active database base objects such as richer `dbo.Customers`,
  `sales.CustomerOrders`, `dbo.CustomerAddresses`, `billing.BillingAddress_0001`,
  `billing.CalculateBillingTotal_0001`, `reporting.GetCustomerAddresses_0001`,
  `dbo.FindCustomerAddress`, `reltest.CompletionLayoutStress`, and
  `reltest.TypedTargets`.
- Prefix-family tables `Belege`, `BelegePositionen`,
  `BelegePositionenDetails` for exact/prefix collision and Smart Alias tests.
- Secondary database richer reporting objects:
  `Customers` with reporting-specific columns, `ActiveCustomerAddresses`,
  `GetCustomerAddresses`, `GetBillingsByCustomer`, `archive.CustomerAddressArchive`,
  `Auftraege`, and `AuftraegePositionen`.
- `tests/fixtures/create-cross-database-fixture.sql` is minimal and does not match
  all current live integration expectations; for example it creates a small
  `dbo.Customers` table while tests expect richer reporting columns in some paths.

### Why The Supplemental Fixture Uses New Schemas

The supplemental script creates new neutral `qpacc`, `qpacc_ref`, and
`qpacc_archive` objects instead of modifying existing `dbo`, `reltest`, `relref`,
`billing`, `sales`, `reporting`, or `archive` fixtures. This avoids disturbing
fixtures that already work for automated or installed-editor tests and gives
manual acceptance a controlled namespace.

The script creates `qpacc.OrderLines` independently from its composite primary and
foreign keys, then adds each constraint through its own idempotent guard. This
prevents a dependency-binding failure from rolling back the base table creation.
Explicit postconditions report a missing table or constraint, and each database
section finishes with a complete expected-object audit so a partial provisioning
run cannot appear successful.

## Manual Acceptance Execution Contract

Use the numbered SQL case with the same number in
`0.11.0-manual-test-cases.sql`. Expected names remain in this document only so
editor word suggestions cannot manufacture false positives from SQL comments.

For every test:

- trigger the native Suggest widget or Signature Help at the stated cursor
- count only Query Puppy for T-SQL semantic items
- ignore every generic editor `abc` suggestion (`abc` is recorded as **Ignore** in
  every table)
- candidates are alphabetical inside an equivalent semantic/group tier unless an
  explicit exact-match, relationship, or compatibility rule is stated
- physical items must retain their complete insert/filter identifier and canonical
  documentation even when visible presentation is shortened
- **RUN ALONE IN A FRESH SQL EDITOR** means paste only that numbered case into a
  new SQL editor before testing; this prevents deliberately incomplete SQL from
  interacting with another case
